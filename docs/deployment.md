# Deploy a ClinicOS staging service

The checked-in `render.yaml` is a Render web-service blueprint. It runs the app with Gunicorn, collects static files, uses a shared database-backed throttle cache, checks the database through `/health/ready/`, and runs migrations before each deployment. The blueprint uses a paid web plan because Render requires a paid service for its pre-deploy migration command.

## Required services and secrets

Create a managed PostgreSQL database in the same region as the web service. Set `DATABASE_URL` to its private connection URL. Keep the application database role non-superuser and without `BYPASSRLS`; the app verifies this and fails closed if the role or tenant policies are unsafe.

Generate a stable field-encryption key once:

```powershell
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Set it as `FIELD_ENCRYPTION_KEY` in the host's secret manager. Back it up separately and retain it across deploys: replacing it makes existing encrypted fields unreadable. Do not put the key in Git, an image, or build logs.

Configure these deployment values before the first build:

- `DATABASE_URL`: persistent PostgreSQL private connection URL
- `FIELD_ENCRYPTION_KEY`: generated Fernet key
- `SITE_URL`: full HTTPS URL users will visit, such as `https://clinic.example.com`
- `DEFAULT_FROM_EMAIL`, `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`: verified SMTP sender details
- `DJANGO_ALLOWED_HOSTS`: set the custom domain when using one; Render's generated hostname is detected automatically
- `DJANGO_CSRF_TRUSTED_ORIGINS`: optional comma-separated full origins when the browser origin differs from `SITE_URL`

`DJANGO_SECRET_KEY` is generated by the blueprint. `DJANGO_DEBUG` is set to false. HTTPS redirects, secure session/CSRF cookies, and a one-day HSTS policy are enabled by default in non-debug mode. Increase HSTS only after confirming the domain and all subdomains are permanently HTTPS capable.

## Release checks

The Render build command installs `requirements.txt` and runs `collectstatic`. The pre-deploy command runs `migrate`, creates the shared cache table, and runs `check --deploy`. Migration `0006_usageevent` is part of the normal migration chain. The instance then starts as a non-root user under Gunicorn.

After the first staging deploy:

1. Confirm `/health/ready/` returns `{"status":"ok"}`.
2. Create the first owner account with `python manage.py createsuperuser` through the host's shell.
3. Sign in, create a clinic, add a synthetic patient, create an encounter, verify the audit chain, and test an invitation with the configured SMTP mailbox.
4. Confirm cookies are Secure over HTTPS and `python manage.py check --deploy` reports no warnings.
5. Run the attack suite and a small benchmark against the staging URL using synthetic records; record the environment and results in `phase7-benchmarks.md`.
6. Verify database backups and perform a restore drill before storing data anyone depends on.

## Vercel and production data

Vercel supports Django through Python Functions, but a Vercel deployment still needs a persistent PostgreSQL provider, the same secrets and trusted-origin configuration, a shared cache backend, and a reliable release step for migrations/cache-table creation. Use Vercel's Django guide for platform-specific entrypoint and release setup.

This learning project is not a certified or audited healthcare service. Keep staging data synthetic. Before handling real patient information, complete the applicable privacy, security, contractual, incident-response, access-review, backup, and disaster-recovery work with qualified reviewers.
